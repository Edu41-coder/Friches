================================================================================
                        I. OBJECTIFS DU BENCHMARK
================================================================================

Ce document synthétise trois analyses complémentaires pour orienter le 
développement de l'Application Friches :

1. VEILLE TECHNOLOGIQUE
   • Identifier les technologies cartographiques et de visualisation
   • Évaluer les performances et limitations
   • Déterminer les choix adaptés au MVP et à la scalabilité

2. BENCHMARK SOLUTIONS EXISTANTES
   • Analyser les plateformes comparables (Cartofriches, SOGEFI, etc.)
   • Comparer fonctionnalités et approches
   • Identifier les meilleures pratiques

3. ANALYSE FONCTIONNELLE
   • Définir les critères d'évaluation (standardisation, qualité, UX)
   • Positionner l'Application Friches dans l'écosystème
   • Dégager des recommandations pragmatiques

A. SOURCES OUVERTES / PUBLIQUES

DATA.GOUV.FR

• Plateforme nationale de référence des friches

• URL : https://cartofriches.cerema.fr/

OPENSTREETMAP (OSM)

C. RECOMMANDATIONS DONNÉES
---------------------------

1. Diversifier les sources pour enrichissement :
   • BASIAS/BASOL : historique industriel + pollution
   • Cartofriches : géolocalisation + fiches
   • Cadastre : surfaces précises + propriétaires

   • Dashboard qualité : complétude, fraîcheur, géolocalisation

            III. SOLUTIONS COMPARABLES - ANALYSE DÉTAILLÉE

A. CARTOFRICHES (CEREMA)
-------------------------

DESCRIPTION
• Plateforme nationale officielle de visualisation des friches
• Portée par le Cerema et partenaires institutionnels
• Géostandard CNIG existant mais lettrage améliorable

POINTS FORTS
✓ Référence publique reconnue
✓ Standardisation géographique CNIG
✓ Intégration native dans outils métiers collectivités
✓ Contribution collaborative collectivités
✓ Fiches descriptives complètes
✓ Historique et traçabilité

LIMITES IDENTIFIÉES
✗ Analytics limitée (pas de graphiques statistiques avancés)
✗ Enrichissement automatique faible (risques, socio-éco)
✗ Détection automatique friches/vacants : non
✗ Interface expérience utilisateur améliorable
✗ Pas de scoring/priorisation multi-critères
✗ API publique limitée

POSITIONNEMENT
• Référentiel institutionnel (vocation catalogue)
• Notre application : vocation analytique et aide décision avancée

B. SOGEFI (EDITEUR SIG)
------------------------

DESCRIPTION
• Éditeur SIG intégrant Cartofriches dans plateforme 
  "Mon Territoire Carto"
• Couches activables API et outils SIG métiers
• Intégration native outils collectivités

POINTS FORTS
✓ Intégration professionnelle SIG
✓ Outils analyse spatiale avancés
✓ Support éditeur et formations

LIMITES
✗ Solution propriétaire (licence commerciale)
✗ Coût pour collectivités
✗ Dépendance éditeur (vendor lock-in)

URL : https://www.sogefi-sig.com/

C. SIT@DEL (DONNÉES PERMIS CONSTRUIRE)
---------------------------------------

DESCRIPTION
• Base nationale permis de construire/démolir
• Utilisée pour détecter automatiquement friches en cours 
  de réaffectation

USAGE
• Croiser données Cartofriches + autorisations urbanisme
• Identifier sites en cours de requalification
• Automatiser mise à jour statuts

URL : https://www.statistiques.developpement-durable.gouv.fr/

D. CEREMA - HACKATHON RST ANALYTICS 2018
-----------------------------------------

DESCRIPTION
• Prototype détection friches industrielles par croisement 
  bases publiques
• Sources : BASIAS, BASOL, ICPE, SIRENE
• Approche semi-automatisée pré-recensement par agrégation multi-source

INNOVATION
✓ Première approche automatisée pré-recensement
✓ Croisement intelligent bases hétérogènes
✓ Réduction temps identification manuelle

URL : https://www.cerema.fr/fr/actualites/challenge-rst-analytics-2018-
      cerema-s-implique-detection

E. SONG ET AL., 2022 - MACHINE LEARNING
----------------------------------------

DESCRIPTION
• Méthode IA croisant occupation du sol + données activité + 
  imagerie Street View
• Détection automatique friches urbaines abandonnées
• Précision 84,9% sur sites identifiés

TECHNOLOGIE
• Machine learning (classification supervisée)
• Features : données cadastre, occupation sol, photos terrain
• Validation terrain croisée

APPLICABILITÉ
→ Inspirant pour phase R&D (détection automatique enrichie)
→ Nécessite dataset d'entraînement conséquent

URL : https://www.researchgate.net/publication/359434888_
      Identifying_urban_candidate_brownfield_sites

            V. BENCHMARK TECHNIQUE - CARTOGRAPHIE
================================================================================

A. LEAFLET.JS
-------------

DESCRIPTION
• Bibliothèque JavaScript open source légère
• Référence pour cartes web interactives
• Plugins riches (MarkerCluster, Draw, etc.)

POINTS FORTS
✓ Léger (~40 KB minifié)
✓ Écosystème plugins très riche
✓ Compatible tuiles OSM gratuites
✓ Clustering efficace >500 points (MarkerCluster)
✓ Courbe d'apprentissage faible
✓ Documentation excellente
✓ Communauté active

LIMITES
✗ Pas de rendu WebGL natif (raster tiles uniquement)
✗ Vector tiles via plugins (moins performant que natif)
✗ Performances limitées > 10 000 points sans clustering

RECOMMANDATION
🟢 RECOMMANDÉ POUR MVP
• Parfait équilibre simplicité/fonctionnalités
• Déploiement rapide
• Maintien facile

APPLICABILITÉ APPLICATION FRICHES
✓ Actuellement utilisé (bon choix)
✓ Clustering actif pour zones denses
✓ Compatible tous besoins MVP et phase 2

B. MAPBOX GL JS
---------------

DESCRIPTION
• Bibliothèque cartographie moderne basée WebGL
• Vector tiles haute performance
• Styles personnalisables avancés

POINTS FORTS
✓ Rendu WebGL natif (performances excellentes)
✓ Vector tiles (zoom fluide, styles dynamiques)
✓ Effets 3D et animations
✓ Design moderne et élégant

LIMITES
✗ Nécessite compte Mapbox (tokens)
✗ Conditions de licence restrictives (changements 2020)
✗ Coût si dépassement quota gratuit
✗ Bundle plus lourd que Leaflet

RECOMMANDATION
⚫ À CONSIDÉRER PHASE 2+
• Si besoins visualisation avancée (3D, animations)
• Si budget pour licences
• Si > 50 000 marqueurs à afficher

APPLICABILITÉ APPLICATION FRICHES
→ Trajectoire possible si :
  • Besoin visualisation 3D bâtiments
  • Très gros volumes de données (> 100k friches)
  • Budget disponible pour licences

C. OPENLAYERS
-------------

DESCRIPTION
• Bibliothèque cartographie JavaScript puissante
• Gestion projections complexes
• Intégration WMS/WFS avancée

POINTS FORTS
✓ Très puissant (projections, vecteurs, raster)
✓ Intégration services OGC (WMS, WFS, WCS)
✓ Gestion projections multiples (pas que Web Mercator)
✓ Pas de dépendance serveur tiers

LIMITES
✗ Courbe d'apprentissage élevée
✗ API plus complexe que Leaflet
✗ Bundle plus lourd
✗ Moins de plugins communautaires

RECOMMANDATION
⚫ POUR CAS AVANCÉS SPÉCIFIQUES
• Si besoins projections Lambert93 etc.
• Si intégration services OGC complexes
• Si besoins analyse spatiale côté client

APPLICABILITÉ APPLICATION FRICHES
→ Pas nécessaire pour MVP
→ Envisageable si intégration WMS DREAL obligatoire

              VII. BACKEND & ARCHITECTURE - RECOMMANDATIONS
================================================================================

A. ARCHITECTURE PHP ACTUELLE
-----------------------------

ÉTAT ACTUEL
• PHP 8+ avec architecture MVC légère custom
• PDO pour MariaDB
• Structure :
  - app/models/ : logique métier et accès données
  - app/views/ : templates HTML/PHP
  - app/controllers/ : contrôleurs routing
  - config/ : configuration BDD
  - public/ : assets (CSS, JS) + point d'entrée

POINTS FORTS
✓ Simplicité déploiement (LAMP/XAMPP)
✓ Contrôle fin de l'architecture
✓ Faible overhead (pas de framework lourd)
✓ Courbe d'apprentissage rapide équipe
✓ Performance correcte pour MVP

LIMITES
✗ Structuration limitée à long terme (scaling)
✗ Pas de tooling avancé (migrations, seeds, CLI)
✗ Sécurité à maintenir manuellement (CSRF, etc.)
✗ Tests unitaires plus complexes à mettre en place

RECOMMANDATION MVP (PHASE 1-2)
🟢 CONSERVER MVC LÉGER ACTUEL
• Adapté parfaitement au MVP
• Ne pas sur-ingéniérer trop tôt
• Focus sur fonctionnalités métier

RECOMMANDATION PHASE 3+ (INDUSTRIALISATION)
⚫ ENVISAGER MIGRATION FRAMEWORK PHP
Si équipe grandit OU besoins complexifient :

Option 1 : Laravel
• 🟢 Écosystème très riche (ORM Eloquent, migrations, queues)
• 🟢 Tooling excellent (Artisan CLI, testing)
• 🟢 Sécurité built-in (CSRF, validation, auth)
• 🟢 Communauté immense
• 🔴 Courbe d'apprentissage si équipe pas familière
• 🔴 Overhead performance (acceptable pour la plupart des cas)

Option 2 : Symfony
• 🟢 Architecture très structurée (bundles, services)
• 🟢 Flexible et modulaire
• 🟢 Performance excellente
• 🟢 Adapté projets complexes long terme
• 🔴 Courbe d'apprentissage élevée
• 🔴 Plus verbeux que Laravel

Recommandation : Laravel si équipe junior/mixte
                 Symfony si équipe senior + besoins complexes

B. BASE DE DONNÉES SPATIALE
----------------------------

ÉTAT ACTUEL
• MariaDB 10.x
• Stockage lat/lon en DECIMAL
• Requêtes filtres standards (=, LIKE, BETWEEN)

FONCTIONNEMENT ACTUEL
✓ OK pour points simples + filtres attributaires
✓ Performance acceptable < 50 000 friches
✓ Pas de besoins spatial avancés immédiat

LIMITES MARIADB SPATIAL
✗ Pas de support PostGIS (fonctions spatiales limitées)
✗ Pas d'index R-Tree performants
✗ Requêtes spatiales complexes (intersections, buffers) limitées
✗ Pas de support natif GeoJSON optimisé

RECOMMANDATION

MVP (PHASE 1-2)
→ CONSERVER MARIADB
  • Suffit amplement pour besoins actuels
  • Ne pas complexifier prématurément

PHASE 2-3 (ANALYSES SPATIALES)
→ MIGRER POSTGRESQL + POSTGIS
  Si besoins émergent :
  • Requêtes spatiales (intersection polygones/points)
  • Buffers (zones autour friches)
  • Calculs distances (friches proches infrastructures)
  • Analyses par bounding box (optimisées)
  • Export GeoJSON natif performant

AVANTAGES POSTGIS
✓ Fonctions spatiales complètes (>300 fonctions)
✓ Index R-Tree très performants (GIST)
✓ Support complet OGC (WKT, WKB, GeoJSON)
✓ Requêtes spatiales standards SQL
✓ Performance excellente gros volumes

MIGRATION MARIADB → POSTGRESQL
• Relativement simple (SQL standard)
• PDO compatible (changement DSN uniquement)
• Scripts migration à prévoir
• Tests complets requis

ALTERNATIVE LÉGÈRE : SPATIALITE
• Extension SQLite pour spatial
• Mono-fichier (pas de serveur)
• 🟢 Simplicité extrême
• 🔴 Pas adapté multi-utilisateurs simultanés
• → Pas recommandé pour production

C. API REST
-----------

ÉTAT ACTUEL
• Endpoints JSON custom (getDataJson, getChartDataJson, etc.)
• Pas de structure REST stricte
• Authentification session PHP

RECOMMANDATION PHASE 2-3
→ STRUCTURER API REST PROPRE
  • Routes RESTful standards :
    GET    /api/v1/friches          → Liste paginée
    GET    /api/v1/friches/{id}     → Détail friche
    POST   /api/v1/friches          → Créer friche (admin)
    PUT    /api/v1/friches/{id}     → Modifier friche (admin)
    DELETE /api/v1/friches/{id}     → Supprimer friche (admin)
    GET    /api/v1/stats            → Statistiques globales
    GET    /api/v1/charts/{type}    → Données graphiques

  • Authentification : JWT ou OAuth2 (phase 3)
  • Rate limiting : protéger API abus
  • Documentation : OpenAPI/Swagger
  • Versioning : /api/v1/ pour rétrocompatibilité

        VIII. PERFORMANCE, HÉBERGEMENT, OPTIMISATIONS
================================================================================

A. OPTIMISATIONS CARTOGRAPHIE
------------------------------

CLUSTERING
• Actif actuellement : Leaflet.markercluster ✓
• Seuil recommandé : >500 marqueurs
• Configuration optimale :
  - maxClusterRadius: 80 (équilibre cluster/détail)
  - disableClusteringAtZoom: 15 (détail à fort zoom)
  - spiderfyOnMaxZoom: true (éviter surcharge visuelle)

LAZY LOADING PAR BOUNDING BOX
• Non implémenté actuellement
• Recommandation PHASE 2 si >10 000 friches :
  - Charger seulement friches dans zone visible carte
  - Requête SQL avec WHERE lat BETWEEN ... AND lon BETWEEN ...
  - Recharger lors déplacement/zoom carte
  - Événement Leaflet : map.on('moveend', loadVisibleFriches)

SIMPLIFICATION GÉOMÉTRIES (si polygones phase 3+)
• Utiliser Douglas-Peucker pour réduire points
• Turf.js côté client ou PostGIS côté serveur
• Réduire précision coordonnées (6 décimales suffisent)

B. OPTIMISATIONS BACKEND
-------------------------

CACHE CÔTÉ SERVEUR
• Recommandation PHASE 2 :
  - Mettre en cache endpoints JSON/GeoJSON
  - Redis ou fichiers cache (APCu)
  - Invalidation lors modification données
  - TTL adapté (ex: 5 min pour stats, 1h pour carte complète)

EXEMPLE CACHE REDIS
```php
// Vérifier cache
$cacheKey = 'friches_geojson_' . md5(json_encode($filters));
$cached = $redis->get($cacheKey);
if ($cached) {
    return json_decode($cached);
}

// Sinon calculer et mettre en cache
$data = $model->findAll($filters);
$redis->setex($cacheKey, 3600, json_encode($data)); // 1h
return $data;
```

INDEX SQL
• Actuellement : à vérifier
• Index recommandés :
  - INDEX sur comm_insee (filtres fréquents)
  - INDEX sur site_type (filtres fréquents)
  - INDEX sur site_statut (filtres fréquents)
  - INDEX sur (latitude, longitude) si requêtes spatiales
  - INDEX composite sur (comm_insee, site_type) si combinaisons fréquentes

PAGINATION SERVEUR
• Déjà implémenté ✓ (LIMIT/OFFSET)
• Vérifier performance > 10 000 lignes
• Alternative OFFSET : cursor-based pagination si problèmes

REQUÊTES OPTIMISÉES
• Éviter SELECT * : sélectionner seulement champs nécessaires
• Utiliser EXPLAIN pour analyser plans d'exécution
• Limiter JOINs (dénormaliser si besoin)

C. OPTIMISATIONS FRONTEND
--------------------------

CDN POUR BIBLIOTHÈQUES
• Recommandation IMMÉDIATE :
  - Leaflet, Chart.js, Bootstrap via CDN
  - Réduction latence (serveurs proches utilisateurs)
  - Cache navigateur partagé entre sites
  - Gratuité

EXEMPLE CDN
```html
<!-- Leaflet -->
<link rel="stylesheet" href="https://unpkg.com/leaflet@1.9.4/dist/leaflet.css" />
<script src="https://unpkg.com/leaflet@1.9.4/dist/leaflet.js"></script>

<!-- Chart.js -->
<script src="https://cdn.jsdelivr.net/npm/chart.js@4.4.0/dist/chart.umd.js"></script>
```

MINIFICATION & COMPRESSION
• Minifier CSS/JS custom (Terser, cssnano)
• Activer compression Gzip/Brotli serveur
• Exemple Apache :
```apache
<IfModule mod_deflate.c>
    AddOutputFilterByType DEFLATE text/html text/css text/javascript application/javascript application/json
</IfModule>
```

LAZY LOADING IMAGES (si photos friches phase 3+)
• Attribut loading="lazy" sur <img>
• Bibliothèques : lazysizes, lozad.js

D. HÉBERGEMENT & INFRASTRUCTURE
--------------------------------

MVP (PHASE 1)
• XAMPP local : parfait pour développement ✓
• Déploiement test : serveur LAMP simple

PHASE 2 (PRODUCTION)
• Hébergement recommandé :
  Option 1 : VPS (OVH, Scaleway, Digital Ocean)
    - 🟢 Contrôle total
    - 🟢 Coût maîtrisé (~10-30€/mois)
    - 🔴 Administration manuelle

  Option 2 : Hébergement managé PHP (o2switch, Infomaniak)
    - 🟢 Administration simplifiée
    - 🟢 Support technique
    - 🔴 Moins de flexibilité

  Option 3 : Cloud (AWS, Azure, GCP)
    - 🟢 Scalabilité automatique
    - 🟢 Services managés (BDD, cache)
    - 🔴 Coût variable (attention facture)

Recommandation : VPS pour phase 2 (équilibre coût/contrôle)

PHASE 3 (SCALING)
• Load balancing si >100 utilisateurs simultanés
• Séparation serveur web / serveur BDD
• CDN pour assets statiques (Cloudflare gratuit)

SÉCURITÉ INFRASTRUCTURE
• HTTPS obligatoire (Let's Encrypt gratuit)
• Firewall (UFW, fail2ban)
• Sauvegardes automatiques quotidiennes
• Monitoring (UptimeRobot gratuit)

E. TUILES CARTOGRAPHIQUES
--------------------------

OSM STANDARD (ACTUEL)
• Tuiles OpenStreetMap gratuites
• ✓ Gratuité totale
• ✓ Pas de clé API
• ⚠ Respecter Tile Usage Policy (pas d'abus)
• ⚠ Pas de garantie disponibilité

ALTERNATIVES SI TRAFIC ÉLEVÉ

Option 1 : MapTiler
• Tuiles raster et vector
• Plan gratuit : 100 000 chargements/mois
• Payant : à partir de 25€/mois

Option 2 : Thunderforest
• Styles variés (Outdoors, Transport, etc.)
• Plan gratuit : 150 000 tuiles/mois
• Payant : à partir de 20£/mois

Option 3 : Esri
• Tuiles satellites et rues
• Gratuit si <2M basemaps/mois
• Qualité excellente

Option 4 : Auto-hébergement tuiles
• TileServer GL (vector) ou mod_tile (raster)
• 🟢 Contrôle total, pas de limite
• 🔴 Infrastructure complexe (stockage, bande passante)
• 🔴 Coût serveur + maintenance

RECOMMANDATION
• Phase 1-2 : OSM standard (suffit < 10k utilisateurs/mois)
• Phase 3+ : MapTiler ou auto-hébergement si budget

================================================================================
                            CONCLUSION
================================================================================

Ce benchmark synthétisé met en évidence plusieurs constats clés :

1. POSITIONNEMENT UNIQUE
   L'Application Friches se positionne en complément de Cartofriches, avec
   une orientation analytique et aide à la décision, là où Cartofriches joue
   le rôle de référentiel institutionnel.

2. CHOIX TECHNIQUES VALIDÉS
   La stack actuelle (PHP MVC léger + MariaDB + Leaflet + Chart.js) est
   parfaitement adaptée au MVP et phases 1-2. Les évolutions technologiques
   (PostgreSQL/PostGIS, Laravel/Symfony, Mapbox GL JS, ApexCharts) ne se
   justifieront qu'en phase 3-4 selon besoins réels.

3. DIFFÉRENCIATION CLAIRE
   • Analytics avancés (graphiques interactifs)
   • Filtres multicritères performants
   • Synchronisation tableau ↔ carte
   • Orientation décision vs catalogue
   • Open source et données ouvertes

4. TRAJECTOIRE PROGRESSIVE
   L'approche par phases permet de valider chaque étape avant d'investir
   dans des technologies plus complexes. Principe "start simple, scale smart".

5. ÉCOSYSTÈME FAVORABLE
   Les sources de données ouvertes (BASIAS, BASOL, Cartofriches, data.gouv)
   et l'écosystème technologique mature (Leaflet, Chart.js, PHP) offrent
   un environnement favorable au développement et à la pérennité du projet.

6. RISQUES MAÎTRISABLES
   Les principaux risques (performance, qualité données, adoption) sont
   identifiés et des stratégies de mitigation sont définies pour chaque phase.


Le succès de l'Application Friches reposera sur :
• Excellence UX/UI (simplicité, rapidité, clarté)
• Qualité et fraîcheur des données (QA automatisée)
• Interopérabilité (API publique, standards CNIG)
• Accompagnement utilisateurs (formations, support)
• Innovation continue (R&D, machine learning phase 4)
