Benchmark / Veille – Application Friches

Panorama solutions, données, et choix technos • Version:

1. Objectifs de la veille

  • Identifier les sources de données fiables pour enrichir la base friches
  • Comparer les solutions de visualisation et d'analyse cartographique
  • Évaluer les choix techniques (carto, charts, backend, base spatiale)
  • Déduire des recommandations pragmatiques adaptées au MVP et à l'échelle

2. Écosystème & Sources de données

Ouvertes / publiques

  • data.gouv.fr – Catalogues territoriaux, jeux officiels
  • OSM (OpenStreetMap) – Fond de plan, POI contextuels (ODbL)
  • IGN / Géoportail – Fonds raster, orthophotos (licences dédiées)
  • BASIAS / BASOL – Sites industriels et pollués (MTE)
  • SIRENE / INSEE – Référentiels entreprises & communes
  • BAN – Base Adresse Nationale (géocodage)
Diversifier les sources pour croiser risques / statuts / propriétaires

Internes / partenaires

  • Inventaires locaux (région, EPCI) – formats CSV/Excel variés
  • Études environnement – campagnes ponctuelles
  • Données cadastrales (via conventions)
Recommandation: définir gabarits CSV + dictionnaire de données.

4. Benchmark fonctionnel

  • Tableau interactif (tri, filtres, pagination) — App: OK • uMap: non • ArcGIS: oui • CartoFriches: limité
  • Carte cluster + popups — App: OK • uMap: basique • ArcGIS/CARTO: avancé • CartoFriches: popups
  • Filtres combinés — App: OK • uMap: limité • ArcGIS/CARTO: oui • CartoFriches: basiques
  • Analytics (charts) — App: MVP • ArcGIS/CARTO: riche • CartoFriches: faible
  • Import standardisé — App: en cours • ArcGIS/CARTO: outils • CartoFriches: non public
  • QA data automatisée — App: à implémenter • ArcGIS/CARTO: scripts • CartoFriches: non communiqué
  • Scoring multi-critères — App: à définir • ArcGIS/CARTO: possible • CartoFriches: non

5. Benchmark technique – Cartographie

Leaflet

  • + Léger, plugin-rich, OSM friendly
  • + Clustering efficace >500 pts
  • − Pas de rendu GL natif (vector tiles via plugins)
Recommandé MVP

Mapbox GL JS

  • + Vector tiles performant, style avancé
  • − Compte/tokens, conditions licence
À considérer phase 2+

OpenLayers

  • + Puissant (projections, vecteurs)
  • − Courbe d'apprentissage, bundle
Pour cas avancés

6. Benchmark technique – Graphiques

Chart.js

  • + Simple, léger, communauté
  • − Limites sur gros volumes / charts complexes
Adapté MVP

ApexCharts

  • + Interactions riches, séries multiples
  • − Poids supérieur à Chart.js
Option phase 2

Apache ECharts

  • + Palette très large, performance
  • − Bundle + API plus vaste
Pour dashboards poussés

7. Backend & Architecture

PHP 8 MVC léger

  • + Hébergement simple (LAMP/XAMPP)
  • + Contrôle fin, faible overhead
  • − Structuration limitée à long terme
Conserver MVC simple pour MVP, envisager Laravel/Symfony si équipe grandit.

Spatial & Base de données

  • MariaDB actuel: OK pour points + filtres de base
  • PostgreSQL/PostGIS: recommandé pour requêtes spatiales (intersections, buffers, bbox)
  • SpatiaLite: léger, mono-fichier
Trajectoire: prototyper sur MariaDB, prévoir migration PostGIS pour analyses spatiales avancées.

8. Performance, hébergement, tuiles

  • Clustering >500 markers, lazy loading par bbox si dataset volumineux
  • Cache côté serveur pour endpoints JSON/GeoJSON
  • CDN pour bibliothèques (Leaflet, Chart.js)
  • Tuiles OSM gratuites (respecter usage) • alternatives: Esri, Carto, MapTiler

9. Conformité & licences

  • OSM: ODbL (attribution requise)
  • Data.gouv / Etalab: Licence Ouverte 2.0 (attribution)
  • RGPD: vérifier champs sensibles (propriétaires)
  • Sécurité: sessions, CSRF, hashage bcrypt (déjà pris en compte)

10. Recommandations rapides

Pour 3 prochains sprints

  • Standard d'import + dictionnaire de données
  • QA géo automatisée (bbox FR, EPSG:4326)
  • Dashboard qualité (complétude, fraîcheur)
  • Lazy loading map par bounds

À moyen terme

  • Étude migration PostGIS
  • Scoring multi-critères avec pondérations
  • Tests utilisateurs (urbanisme/analyste) réguliers
